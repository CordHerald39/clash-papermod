更新 Linux 上的 Clash Verge Rev 之前，先记下当前安装方式。发布页同时提供 DEB 与 RPM，并按 amd64/x86_64、arm64/aarch64、ARMv7 给出多份文件。仓库区分 Stable、已废弃的 Alpha、以及可能存在缺陷的 AutoBuild。升级后系统服务还可能因版本或协议不兼容而要求重新安装。没有这些记录，失败时无法判断该继续用 apt、改用 dnf，还是该重装服务。

## 适用条件

适用于准备更换发布标签、在 AutoBuild 与 Stable 之间切换、或即将修复服务模式与 Sidecar。只改订阅、不替换安装包时不需要这一步。连当前版本号都说不清时，更应先记录再更新。

## 记录包格式、架构和频道

1. 记录包格式：当时用 `apt ./路径` 安装 `.deb` 则记 Debian 系 DEB；用 `dnf ./路径` 安装 `.rpm` 则记 Red Hat 系 RPM。用 `dpkg -l` 或 `rpm -q` 确认包仍在数据库中，避免把解压运行误记成已安装。
2. 记录架构：对照文件名中的 amd64、arm64、armhf 或 x86_64、aarch64、armhfp，并再执行 `uname -m` 写在旁边。
3. 记录频道与标签：Stable 为正式版、适合日常使用；AutoBuild 为滚动更新、可能存在缺陷；Alpha 已废弃。更新时保持同一频道、同一家族、同一架构，不要用另一种包格式覆盖。
4. 判断依据：记录应能唯一对应发布页上的某一个资源文件，而不是只写「Linux 版」。

## 记录内核拉起方式

内核可能由系统服务拉起，也可能走 Sidecar。开发说明指出服务未安装则以 Sidecar 启动。

1. 写下是否安装过系统服务、是否修复或重装过。升级后不兼容会提示重装服务；重装后可能内核缺失、无法继续使用 Sidecar；Linux 上修复服务后曾无法启动内核或开启 TUN。
2. 写下更新前内核是否实际在运行，不要只抄「服务模式」——内核未运行时首页仍可能显示服务模式。
3. 若数据目录曾用提升权限访问，注明所有权风险，更新不会自动消除该条件。
4. 判断依据：更新失败后能对比「更新前服务能否拉起内核」，才能区分安装包问题和服务组件问题。

## 记录缺失或更新失败时下一步

查不到包数据库记录时，先停止更新，补齐文件名、来源与版本标签，不要用另一种格式覆盖。出现服务不兼容提示时按提示重装服务，而不是改订阅。重装后 Sidecar 或内核不可用，对照更新前记录优先处理服务与内核文件。把更新前记录和新报错一起保存，再决定是否留在原频道，并仅在同一格式与架构上升级。
