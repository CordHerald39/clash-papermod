重启后策略组回到另一节点，先检查是选择没有保存，还是原节点已经不存在。mihomo 全局配置中的 `profile.store-selected` 用于保存 API 对策略组的选择，供下次启动使用。它不保证订阅未来仍含同一节点，也不保存所有客户端界面偏好。

## 重启前写下可比较的信息

在本机记录客户端与内核版本、启用的配置、策略组名称、选中节点以及接管状态。若组内使用自动选择，下一次切换还可能是策略本来的行为，不能把它当成手动选择缓存丢失。

保存记录只需显示名与设置，不需要完整订阅令牌。若多个配置都有同名策略组，也要把配置名称一起记下，避免比较的其实是不同对象。

## 查看真正生效的缓存字段

以下是字段说明片段，应合并进既有 profile，不能替代完整配置：

```yaml
profile:
  store-selected: true
```

确认客户端最终生成的配置保留该值。若客户端自行管理选择，仍要结合其说明；内核字段定义不能被理解成每个图形界面都采用同一种持久化机制。

相邻的 `store-fake-ip` 保存 fake-ip 映射表，职责不同。不要为了节点选择问题清空 DNS 映射，或误以为开启 store-fake-ip 就能保存策略组选择。

## 用正常退出建立对照

在手动选择组里选定节点，正常退出并重启，检查配置、组名和节点是否仍相同。若重启期间资源更新，先确认原节点是否仍在、名称是否变化，再解释缓存行为。被资源删除的节点不能靠缓存重新创建。

若节点存在、配置一致且选择仍丢失，记录上述字段、正常退出步骤和客户端版本，按项目支持入口反馈。别通过复制不明数据库文件或改系统权限解决；这些操作会引入新的状态问题。
