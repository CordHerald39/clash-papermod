## 适用条件与要记录的边界

给电脑端教程笔记标注版本边界，适用对象是 Clash Verge Rev 这一图形界面，而不是把所有名称含 Clash 的实现当成同一份步骤。仓库说明该项目是 Clash Verge 的延续，基于 Tauri 的 Clash Meta GUI，内置 Clash.Meta(mihomo) 内核，并支持切换 Alpha 版本内核。因此笔记必须同时写下「界面发行」和「内核通道」，二者变化不会自动对齐，也不能写成同一个数字。

边界完整还要满足三点。第一，版本以发布页的 `tag_name` 为准，例如 v2.5.7、v2.5.6、v2.5.5，不使用口头上的「当前」。第二，通道按仓库对发行版的划分来写：Stable 为正式版，高可靠性，适合日常使用；Alpha 已标明废弃；AutoBuild 为滚动更新版，适合测试反馈，可能存在缺陷。第三，平台与安装包形态必须写入，因为 Windows 发布说明写明不再支持 Win7，且同一标签下仍有 x64、ARM64、是否内置 Webview2、macOS 芯片类型、Linux 的 DEB 与 RPM 等差异。

判断依据是：安装包文件名中的版本数字、发布说明里按 Windows / macOS / Linux 分组的修复条目、以及 Stable 与 AutoBuild 的获取分工。其中任一项与读者环境对不上，就把该段步骤标成越界，停止套用。

## 按发行说明写下限、上限和互斥项

第一步，在笔记开头抄录完整版本名，例如 Clash Verge Rev v2.5.7。若某条教法依赖发行说明中的修复，以该修复所在标签为操作下限。v2.5.5 写明优化文件错误日志，显示具体文件路径和失败原因，则「用路径加原因判断文件类失败」不得用于更早标签。v2.5.6 写明代理集合、规则集合在订阅响应较慢时，更新不应只误报失败、而应能看到真实失败原因，则「根据真实失败原因区分更新失败」的下限是 v2.5.6。v2.5.7 写明服务自身的运行日志会保存到文件，便于追查内核被停止的原因，则「用服务日志追查内核停止」的下限是 v2.5.7。

第二步，对尚未逐条核对的更新，上限标为未核验，禁止用更新的包去证明旧笔记仍然成立。第三步，把同一主题在修复前后拆成互斥段落。例如 DNS 覆写：v2.5.7 修复「订阅包含自定义 DNS 时，确认开启的 DNS 覆写在重启应用后被自动关闭」；v2.5.5 还涉及空内容报错、已填写字段被 Merge 或 Script 覆盖、空字段继续使用扩展配置。修复前与修复后的判断条件不同，不能写进同一条通用步骤。

第四步，平台专项单独成行。v2.5.7 分别列出 Windows 系统盘根目录删除权限被误判、macOS 启动或重启时偶发内核启动失败并误提示需要更新系统服务、macOS 与 Linux 在服务模式停止或重启内核时直接强制结束导致最后日志丢失。这些文字只允许出现在对应系统段落。凡涉及服务模式、TUN、系统代理、Sidecar 的步骤，必须带系统名，否则视为边界缺失。第五步，把 Merge、Script 等配置增强与内核是否切换为 Alpha 通道分成两行标注，避免把内核能力和界面发行写成自动同步。

## 对不上版本时的下一步

若无法在发布页找到与读者一致的 `tag_name`，先根据安装包文件名读取版本数字，再打开同一标签的说明，而不是沿用笔记里的旧步骤。若对方使用 AutoBuild，笔记中所有按 Stable 写法给出的判断一律作废，改以该滚动通道的说明为准。若问题属于服务模式或 TUN，而当前标签仍在说明权限误判、服务残留、用户目录位于外置磁盘、服务停止后系统代理仍指向失效端口等约束，将该段标记为受服务安装状态限制，不要补充官方未记载的操作路径。若不能确认项目是否为该 GUI，先阅读仓库首页的产品定义；不匹配则整份电脑端笔记不适用，也不要把内核手册与图形界面发布说明拼成同一条时间线。
