测试结束后恢复原有模式与选择，核心是把运行模式改回试验前的值，并处理 API 可能写入的策略组选择。官方运行模式包括 `rule`（规则匹配）、`global`（全局代理，需要在 GLOBAL 策略组选择代理或策略）、`direct`（全局直连）。此项拥有默认值，默认为规则模式。因此多数人试验前的稳态是 `mode: rule`；若你试验前本来就是 `global` 或 `direct`，应恢复到试验记录里的原值，而不是一律写成默认。`profile.store-selected` 为 true 时，会储存 API 对策略组的选择供下次启动使用，只改 `mode` 而不处理这项，重启后仍可能停在试验时选中的 GLOBAL 或其他策略组出站。

## 先按记录恢复 mode，再处理 GLOBAL 选择

适用条件：对照试验已经结束，需要回到日常规则匹配（或你原本的 direct/global），并且希望策略组选择与试验前一致。判断依据：`mode` 只负责运行模式；策略组选择是另一条状态，API 改过且 `store-selected` 开启时会被持久化。

具体操作：打开全局配置，把 `mode` 改回试验记录中的原值。若记录缺失，资料给出的默认是规则模式，可恢复为 `mode: rule`。若试验期间曾把模式设为 `global`，恢复 `rule` 后，GLOBAL 组里为试验临时挑选的代理或策略不必再承担“全局出口”角色，但组内当前选中项仍可能留在那里。接着检查 `profile`：`store-selected` 控制是否储存 API 对策略组的选择；`store-fake-ip` 控制是否储存 fakeip 映射。日常若依赖启动后自动回到上次节点，应保持与试验前相同的 `store-selected` 取值，并用 API 把各策略组选回试验前的出站。不要在未记录原选择的情况下随意清空该项，否则下次启动行为会与试验前不同。

## 把仅为排查改过的观察项恢复原状

日志级别、进程匹配、入站范围若在排查中改过，也应一并恢复，否则“模式已经改回”仍会改变你看到的现象。`log-level` 的 `debug` 会尽可能输出运行中所有信息，`info` 含一般运行内容，`warning`/`error` 更少，`silent` 不输出。把排查时升高的级别改回你原来的日常级别。`find-process-mode` 若曾从 `strict` 改成 `always` 或 `off`，按记录改回；资料说明 `off` 推荐在路由器上使用，桌面与路由不应用同一次试验的值覆盖长期配置。`ipv6` 默认 true，若试验中关闭过内核 IPv6 接收，恢复原值以免后续连接路径变化。

入站项同样如此。`allow-lan`、`bind-address`、`lan-allowed-ips`、`lan-disallowed-ips`、`authentication`、`skip-auth-prefixes` 只应在试验需要扩大或缩小接管范围时改动。试验结束把它们改回记录值，避免局域网设备或未认证客户端继续进入代理端口。外部控制器 `external-controller`、`secret`、CORS、Unix socket、namedpipe、TLS API 若只是为了临时读写 `mode` 而放宽监听或留空密钥，应按资料中的安全说明收紧：socket 与 namedpipe、以及 API 上的 DOH 路径不会验证 secret，试验用完应避免继续暴露。

## 恢复后仍停留在试验状态时的下一步

若文件已是 `mode: rule`，启动后仍像全局代理，下一步检查 API 与持久化，而不是反复保存同一份 YAML。读取外部控制器返回的运行模式和策略组选择，确认是否与文件一致。若 API 仍显示 `global`，说明运行中状态未加载该文件，需要按你实际部署方式让内核重新加载配置（本页未给出具体客户端菜单，不以未记载的按钮代替）。若模式已是 `rule` 但出站仍是试验节点，检查 `store-selected` 是否在试验中把 GLOBAL 或其他组的选择写盘，并用 API 改回原选择后再确认该项是否仍为你需要的 true/false。

`store-fake-ip` 若在试验中开启，域名可能继续使用原有映射地址，这与运行模式无关，但会造成“好像没恢复”的错觉；是否关闭该项取决于你日常是否依赖 fakeip 缓存，只要求与试验前一致。完成上述核对后，用与试验相同的目标再看日志：`log-level` 已恢复则信息量应回到日常；进程匹配已恢复则进程信息的有无应回到日常。只有 `mode`、策略组选择、日志级别、进程匹配和入站范围都与试验记录中的“原状”一致，才算测试结束时的恢复完成。
