电脑端把故障处理完后，有效修复条件是一组以后还能对照的约束：发行通道、版本标签、操作系统、服务模式或 Sidecar、订阅是否含自定义 DNS、是否同时使用 Merge 或 Script，以及当时能否看到服务或文件错误日志。仓库写明配置与日志仅保存在本地，因此记录要能在本机复核，而不是只留下“已经恢复”。

## 适用条件

内核无法启动、服务模式或 TUN 不可用、系统代理状态读取报错、重启后 DNS 覆写被关掉、不同来源订阅或规则集共用缓存路径导致服务模式无法启动内核、停止或重启服务时最后日志丢失，都适合在现象刚消失时记账。首次以管理员身份启动后数据目录所有权不符、重新安装服务后内核缺失、内核未运行时首页仍显示服务模式，也应对齐记录，因为“界面像服务模式”和“内核确实在跑”不是同一件事。发布说明按 Windows、macOS、Linux 分段，跨系统复述同一句会失去判断价值。

通道必须写明。正式版（Stable）说明为高可靠性、适合日常使用；AutoBuild 为滚动更新、可能存在缺陷。记录要能回答安装包来自发布页的哪一个 tag，以及本机是否仍满足该 tag 所列的操作系统前提（例如 Windows 发行说明写明不再支持 Win7）。

## 字段与判断依据

到发布页核对 tag（例如 v2.5.5、v2.5.6、v2.5.7）及平台分段，说明里的因果与本机一致才算有效。

Windows 应记下：是否未安装服务却以普通权限运行；系统盘根目录删除权限或系统隔离权限是否被误判；是否有旧版服务残留；服务停止后是否约两分钟才显示窗口；安装失败是否出现「program not found」；路径或目录权限失败时的原因原文。

macOS 应记下：启动或重启是否偶发内核失败并误报需要更新系统服务；VPN 接管或开机网络未就绪时，服务内核、TUN、系统代理状态是否同时异常；使用 `ipconfig set` 手动配置网卡后是否无法设置系统代理；残留服务进程、外置磁盘上的用户目录、用户组无法解析；内核意外停止后系统代理是否仍指向失效端口。

Linux 应记下安装或修复服务后是否仍无法启动内核或开启 TUN。macOS/Linux 共用项：停止或重启是否强制结束内核，造成最后日志丢失。

订阅含自定义 DNS 时，要记录确认开启的 DNS 覆写是否在重启后被自动关闭，以及空内容报错、初始值覆盖、已填写字段被 Merge 或 Script 覆盖、空字段是否继续使用扩展配置。文件错误日志会给出路径和失败原因，应抄录原文。服务运行日志保存到文件后，可用来追查内核被停止的原因；窗口恢复后若仍提示尚未解决的错误，也要写入。

## 落盘步骤与失败下一步

笔记中依次写：发布页与仓库地址、tag 与通道、系统、服务或 Sidecar、是否 TUN、当时网络是否就绪、是否 VPN 接管、是否手动配置网卡、订阅与 DNS 覆写、Merge/Script、缓存是否共用、日志路径与原因。再对照该 tag 修复条目，标完全对齐或部分对齐。

对不上时，先看是否在正式版与 AutoBuild 之间切换，再看是否套错平台条目。Windows 服务安全检查失败会直接说明原因，应补录原文，避免只留下“服务无法启动内核”。数据目录所有权不符、管理员首次启动、重装后内核缺失，要把相关提示留下。若退出过程仍被强制结束、最后日志丢失，把“退出日志不完整”标成未满足条件，等服务日志可保存时再补一次完整退出记录。
