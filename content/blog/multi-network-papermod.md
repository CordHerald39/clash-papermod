## 适用条件：什么情况下记录会串网

只有在你需要对比不同接入网络下的同一类故障时，才需要把排查记录按网络拆开保存。内核现象由当时的全局配置共同决定，而不是一份可以跨网复用的固定画像。运行模式 `mode` 默认为规则模式，也可设为 `global` 或 `direct`；出站接口由 `interface-name` 指定；`ipv6` 控制是否接受 IPv6 流量且默认为 true；`allow-lan` 决定其他设备能否经过代理端口访问互联网；`bind-address` 限制绑定地址；日志由 `log-level` 控制，并且只在控制台和控制页面输出。换网之后如果仍引用上一份未标注出口、模式和监听范围的结论，就会把不同网卡、不同地址族、不同准入范围下的结果写成同一判断。

`profile` 里的 `store-selected` 为 true 时，会储存 API 对策略组的选择供下次启动使用；`store-fake-ip` 为 true 时会储存 fakeip 映射，域名再次连接时使用原有映射地址。这两项会让上一网络周期的选择或映射在重启后仍然在场。判断依据是：归档中必须同时写明启动时间、上述两项的真假、以及本次是否曾经通过 API 改选。缺这三项，就不能把控制页面上的当前选择当作本网络的新结论。

## 按网络保存记录的具体步骤

切换网络并准备复现前，先建立独立归档，不要把新日志追加到旧文件末尾，也不要只改标题不改正文。

第一步，复制当时全局配置中与网络相关的字段，至少包括 `mode`、`interface-name`、`ipv6`、`allow-lan`、`bind-address`、`lan-allowed-ips`、`lan-disallowed-ips`、`log-level`。若在 Linux 上设置了 `routing-mark`，一并写入。判断依据：禁止连接的地址段优先级高于允许段；`bind-address` 为星号表示绑定所有 IP，也可以绑定单个 IPv4 或单个 IPv6。家庭宽带、公司网络与手机热点的接口名和地址段通常不同，缺任一字段就无法解释为何只在某一网络失败。

第二步，注明本次日志级别。`silent` 不输出；`error` 仅输出发生错误至无法使用的日志；`warning` 还包含不影响运行的错误；`info` 再加一般运行内容；`debug` 尽可能输出运行中所有信息。判断依据：若记录声称没有报错但当时是 `silent`，该断言无效。同一段落不要混用不同日期、不同级别的输出，因为各级别覆盖的信息集合不同。

第三步，把本时间窗的控制台或控制页面输出保存为与网络名称对应的文件，正文不要改写。若使用 RESTful API，记录 `external-controller` 地址以及是否配置 `secret`。从 Unix socket 或 Windows namedpipe 访问 API 不会验证密钥，必须单独标注，以免和需密钥的 HTTP API 混读。监听地址若从回环改为全接口监听，现场是否暴露到当前网段也要写入快照。

第四步，若 `store-selected` 或 `store-fake-ip` 为 true，在归档开头写明策略组选择或映射可能继承自上次启动。若已开启 `unified-delay` 或 `tcp-concurrent`，也要注明：前者会计算 RTT 以消除握手带来的延迟差异，后者会对解析出的所有 IP 并发连接并使用第一个成功的连接。跨网络比较延迟或连通性时，这两项会改变量纲，不能省略。

## 判断是否混用以及失败时下一步

可用下列规则判断记录是否已经串网：同一段落同时讨论未标注的出站接口与多种接入方式；未写 `mode` 却比较全局代理与规则分流；在 `store-fake-ip` 为真时把旧映射下的成败当成新的解析结论；用 `silent` 下的空白输出证明某网络正常。命中任一条，该记录只能当线索，不能当结论。

失败时下一步：先确认级别不是 `silent`；再核对 `interface-name` 是否仍指向已断开的网卡；然后检查 `lan-disallowed-ips` 是否把当前网段列入禁止范围。需要更多现场信息时，仅在本网络的复现窗口把 `log-level` 提到 `info` 或 `debug`，结束后改回。`find-process-mode` 在 `always`、`strict` 与 `off` 之间的差异会改变日志里能否出现进程信息，文档说明路由器上推荐 `off`，不要把无进程字段的日志和电脑上 `strict` 的日志直接对比。仍不足以分离结论时，只保留配置片段与原始日志，不要补充该全局配置说明未记载的原因。
