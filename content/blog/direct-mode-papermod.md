排查阶段把 `mode` 设为 `direct`，只是临时使用全局直连。手册中与之对应的恢复方式，是把运行模式改回 `rule` 或 `global`。该项默认值为规则模式，因此要恢复按规则选路时应使用 `rule`。若需要全部走代理，则使用 `global`，并且必须在 GLOBAL 策略组选择代理或策略。恢复模式不等于自动还原出站接口、路由标记或日志级别，也不等于退出客户端。

## 适用条件

在下列条件同时满足后再恢复：对照实验已经得出结论；排查期间改过的全局项已记录；明确要回到规则匹配还是全局代理。直连对照尚未完成时改回 `rule`，规则会重新介入，无法解释新的成败。若排查中改过 `interface-name`、`routing-mark`、`ipv6`、`find-process-mode`、`allow-lan` 等，恢复 `mode` 时必须同时决定这些项是还原还是保留，否则会出现“模式已恢复但出站仍绑错网卡”的二次问题。`unified-delay` 用于计算 RTT 以消除不同类型节点握手带来的延迟差异，它影响的是节点延迟比较，不能代替 `mode` 的恢复。

## 操作步骤

1. 将 `mode` 从 `direct` 改为与排查前目标一致的 `rule` 或 `global`。省略字段时官方默认才是规则模式，不要把省略理解成某个自定义值。
2. 若恢复为 `global`，在 GLOBAL 策略组中完成代理或策略的选择。缺少这一步，全局代理模式没有完整的出站选择。
3. 处理 `profile.store-selected`。为 true 时会储存 API 对策略组的选择，供下次启动使用。排查期间若经 API 改过策略组，只改 `mode` 可能仍沿用被储存的选择。
4. 把 `log-level` 从排查用的 `debug` 调回日常级别。`info` 含一般运行内容以及 error、warning；不需要长期停留在尽可能输出全部信息的级别。日志仍只在控制台和控制页面输出。
5. 重新加载配置，确认实际运行模式已不是 `direct`。外部控制器只能说明 API 仍可访问，不能替代核对 `mode` 字段。

## 判断依据与失败时下一步

恢复成立的依据是：加载后的 `mode` 为 `rule` 或 `global`；在 `global` 时 GLOBAL 策略组已有选择；为对照而改的出站接口、路由标记、IPv6、进程匹配和局域网放行已按计划还原或确认保留。若恢复后立刻再次失败，不要马上在直连与规则之间循环切换：先检查是否加载错文件、是否仍停留在 `direct`、`global` 下是否未选择 GLOBAL 出站。规则模式异常而全局直连正常，说明问题在规则或出站代理，而不是恢复步骤本身，应停止反复改 `mode`。若 API 中的策略组选择与文件不一致，核对 `store-selected`。Unix socket、namedpipe 和 DOH 路径不验证 secret，它们不能当作“策略已恢复”的判据。
